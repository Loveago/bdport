ARCHITECTURAL PRINCIPLES OF THIS CLONE:
1. PURE SINGLE-ORDER ARCHITECTURE:
   - Every transaction in the system is an independent `Order`.
   - The complex parent-child "Batch Order" layer (OrderBatch, ExportBatch, batch progress bars,
     batch codes, and batch status recomputation) has been removed.
   - Resellers can submit multiple recipients at once (via bulk paste or spreadsheet upload), but the
     system decomposes them immediately into clean, individual, self-contained `Order` records.
   - Order management, status transitions, exports, dispute reporting, and developer APIs all operate
     directly on individual orders.

2. EXTENSIBLE MULTI-API TELECOM PROVIDER SETUP:
   - Vendor-agnostic Multi-API architecture.
   - Administrators can configure multiple upstream telecom API providers (e.g. Provider A, Provider B),
     set their API keys, base URLs, request headers, and assign which telecom network or bundle type routes
     to which provider (e.g. MTN -> Provider 1, Telecel -> Provider 2, AirtelTigo -> Provider 3).
   - All outgoing telecom provider requests, responses, status codes, and latencies are recorded in an
     audit ledger (`OrderApiLog`).
   - Supports automated dispatch, webhook callbacks, and periodic status polling without hardcoded vendor locks.

1. SYSTEM OVERVIEW & ARCHITECTURAL FOUNDATION
====================================================================================================
MyCediNet is a high-performance telecom data bundle provisioning and reseller platform operating in Ghana.
It bridges telecom data wholesalers and end-users through automated APIs and reseller tools.

Target User Personas:
1. Retail Customers: Purchase data bundles directly with instant MoMo/Card payment.
2. Resellers & Agents: Submit multiple customer orders simultaneously, manage client lists,
   open custom-branded white-label storefronts, and earn withdrawable cash commissions.
3. Developers & Enterprise Partners: Integrate data bundle fulfillment into external applications,
   websites, or ERP systems using an authenticated REST API.
4. Administrators & Operations Staff: Oversee provider order dispatching, user balances,
   telecom provider routing, dispute tickets, and platform settings.

Supported Telecom Networks in Ghana:
- MTN Ghana (1GB to 100GB+)
- Telecel Ghana (formerly Vodafone Ghana, 1GB to 50GB+)
- AirtelTigo Ghana (AT iShare & AT Big Time allocations)

Core Architectural Highlights:
- Unified Multi-Domain VPS Hosting: Main application (`mycedinet.com`) and white-label storefronts
  (`mycedinetstore.com` or `mycedishop.com`) run from a single Next.js deployment.
- Direct Single-Order Processing: Orders are processed individually with atomic financial debits,
  clear order codes (`CF-OR-01042`), and granular status tracking.
- Multi-Provider Telecom Abstraction: Clean adapter interface for upstream telecom gateways with
  per-network routing rules, automated dispatch, and fallback staging.
- Decoupled Financial Ledgers: Separate user wallet (for bundle purchases) and storefront commission
  wallet (for reseller profits in integer pesewas).
- Automated "Send & Claim" MoMo Top-Up: Real-time Android SMS webhook parsing and automatic credit.

3. MULTI-DOMAIN ROUTING & REWRITE ARCHITECTURE
====================================================================================================
A single Next.js application serves both domains through Next.js Edge Middleware (`src/middleware.ts`):

Main Platform (`mycedinet.com`):
- Serves `/` (redirects to dashboard or login), `/login`, `/register`, `/forgot-password`, `/reset-password`.
- Serves `/dashboard/*`: Reseller operations (Buy Now, Send Orders, Orders, Packages, Billing, Storefront, API).
- Serves `/admin/*`: Restricted to `ADMIN` and `MANAGER` roles.
- Serves `/v1/*`: Public Developer REST API.
- Handle Shortcut: Visiting `mycedinet.com/@loveagostore` redirects to `https://mycedinetstore.com/loveagostore`.

Dedicated Storefront Domain (`mycedinetstore.com` or `mycedishop.com`):
- Security Restriction: Any access to `/admin` or `/dashboard` redirects to `https://mycedinet.com/login`.
- Clean Customer Rewrites:
  * `mycedinetstore.com/` -> Internally rewritten to `/store` (Discovery homepage).
  * `mycedinetstore.com/:slug` -> Internally rewritten to `/store/:slug` (Reseller store).
  * `mycedinetstore.com/:slug/:network` -> Internally rewritten to `/store/:slug/:network` (Carrier bundles).
  * `mycedinetstore.com/:slug/track` -> Internally rewritten to `/store/:slug/track` (Order tracker & disputes).
  * `mycedinetstore.com/:slug/order/:reference` -> Internally rewritten to `/store/:slug/order/:reference` (Receipt).
  * Dedicated favicon & icons: `/favicon.ico` rewrites to `/store/icon.svg`.

5. AUTHENTICATION, REGISTRATION MODES, RBAC & SECURITY SYSTEM
====================================================================================================
User Roles & Permissions:
- `ADMIN`: Full system authority (system settings, user balances, multi-provider API setup, audit logs).
- `MANAGER`: Operational management (orders, refunds, delivery dispute resolution, verification lists).
- `SECRETARY`: Front-desk support. Access restricted to paths in `secretary_allowed_pages`. Can log in without OTP.
- `RESELLER` / `AGENT`: Places data bundle orders, accesses Developer API, opens customized Storefronts.
- `USER`: Retail consumer. Buys data bundles and tracks personal orders.

User Statuses:
- `ACTIVE`: Normal access.
- `DISABLED`: Account blocked. Immediate rejection at middleware.
- `FROZEN`: Account locked from creating new orders or requesting payouts.
- `PENDING_PAYMENT`: Awaiting initial registration fee payment via Paystack.

Registration Workflows (`POST /api/auth/register`):
1. Admin Gate: Controlled via `allow_user_registration` setting.
2. Signup Code Verification: Controlled via `signup_code_mode` ("DISABLED", "OPTIONAL", "REQUIRED").
   - When REQUIRED: Validates existence, expiry, and available usages. Atomically claims usage in Prisma transaction.
3. Optional Registration Fee:
   - Configured via `signup_fee_enabled` ("true"/"false") and `signup_fee_amount` (e.g. "10.00").
   - If enabled: Creates user with `status: "PENDING_PAYMENT"`, initializes Paystack transaction,
     returns `authorizationUrl` to frontend. User is activated upon payment callback (`/api/auth/register-fee/callback`).

Login & Email OTP Two-Factor Authentication (`POST /api/auth/login`):
1. Verifies email & bcrypt password hash.
2. Admin toggle: `login_otp_enabled` ("true"/"false"):
   - If disabled (or SECRETARY with `secretary_login_without_otp === "true"`):
     Directly sets `mycedinet_session` JWT cookie.
   - If enabled:
     * Generates a 6-digit numeric OTP code (`crypto.randomInt(100000, 1000000)`).
     * Creates a signed JWT ticket (10-minute expiry) containing HMAC hash of code and single-use `jti`.
     * Sends code to user's email via Brevo transactional email API.
     * Returns `{ requiresOtp: true, ticket: "..." }`.
3. Verify OTP (`POST /api/auth/verify-otp`):
   - Validates ticket, matches code, enforces single-use replay protection, sets session cookie.

Session Management & Revocation:
- Stateless signed JWT stored in HTTP-only `mycedinet_session` cookie (7-day duration, Lax).
- Payload includes `sub: userId`, `email`, `role`, and `tv: tokenVersion`.
- Global Revocation: Incrementing `user.tokenVersion` in database instantly revokes all active sessions.

7. USER ORDERING ENGINES: BUY NOW & MULTI-RECIPIENT SINGLE-ORDER DISPATCH
====================================================================================================
Pure Single-Order Philosophy:
- Every order placed is recorded as an independent `Order` row in the database.
- There are NO parent `OrderBatch` wrappers, NO batch codes (`CF-BATCH-...`), and NO batch status polling.

1. "Buy Now" Instant Purchase (`/dashboard/buy-now`):
   - Fast single-bundle purchase.
   - User selects carrier brand (MTN yellow, Telecel red, AT navy).
   - Filter chips: All, Popular, Light (<3GB), Heavy (5GB+).
   - Recipient phone input: Normalizes `+233`/`0` to 10-digits, verifies network prefix.
   - Deducts user's `balance`, inserts single `Order`, triggers provider dispatch.

2. Multi-Recipient Send Orders (`/dashboard/send`):
   - Resellers frequently need to submit 10, 50, or 200 orders at once.
   - Reseller inputs orders via:
     * Spacious Bulk Paste Textarea: Accepts any format (`0241234567 5GB`, `0501234567, 10`, `0271234567 - 2.5GB`).
     * Spreadsheet Upload (.xlsx / .csv): Auto-detects Phone & Volume columns using ExcelJS.
   - Pre-Submission Client Protections:
     * Ported Number Modal: Warns if phone prefix belongs to a different network and asks for confirmation.
     * MTN Verification Check: Warns if MTN numbers are not verified and provides 1-click submission.
     * Insufficient Balance Modal: Shows deficit, provides 1-click button to copy orders back to clipboard,
       and offers top-up link.
     * Browser Draft Autosave: Preserves draft in `localStorage` across page reloads.
   - Direct Single-Order Submission (`POST /api/orders`):
     * The server iterates through the parsed lines.
     * In a single atomic Prisma transaction:
       - Verifies user's total wallet balance covers all order lines.
       - Deducts `user.balance` for the total cost.
       - Creates a single `WalletTransaction` of type `DEBIT`.
       - Inserts each recipient line as an independent `Order` record with a unique order code (`CF-OR-01042`).
     * Returns the array of created single orders.
     * Triggers asynchronous telecom provider dispatch for each order.

8. ORDER LIFECYCLE, STATUS MACHINE & DATA PRIVACY SANITIZATION
====================================================================================================
Order Statuses:
- `PENDING`: Order recorded and debited; queued for telecom dispatch.
- `PROCESSING`: Dispatched to upstream telecom provider API.
- `SUCCESS`: Confirmed delivered by telecom carrier.
- `FAILED`: Delivery failed by carrier (inactive SIM, invalid number, network failure).
- `CANCELLED`: Aborted before delivery attempt.
- `REFUNDED`: Failed/cancelled order refunded; funds credited back to user's wallet.

Status Transition Rules:
- PENDING -> PROCESSING, SUCCESS (admin override), FAILED, CANCELLED.
- PROCESSING -> SUCCESS, FAILED, CANCELLED.
- SUCCESS -> REFUNDED (admin override), FAILED (admin override).
- FAILED -> PROCESSING, PENDING, REFUNDED.
- CANCELLED -> REFUNDED.
- REFUNDED -> Terminal state.

Automated Refund Mechanics:
- When an order transitions to `REFUNDED`:
  * Atomically increments `user.balance` by `order.amount`.
  * Creates `WalletTransaction` of type `REFUND`.
  * Records actor and reason in `OrderStatusHistory`.
  * If the order originated from a Reseller Storefront, reverses the commission in `StorefrontWallet`.

Data Privacy & Note Sanitization (`src/lib/types.ts`):
- All status notes, logs, and failure reasons visible to users or public storefront buyers are passed through
  `sanitizeCustomerRefundNote` and `sanitizeCustomerFacingText`.
- Strips upstream provider names and wholesale costs:
  * Example: Provider error `"Refunded GHS 18.75 on UpstreamProvider"` becomes `"Refunded GHS 25.00"` (reflecting the user's purchase price).
  * Example: `"dispatched via UpstreamProvider API"` becomes `"Dispatched for automated delivery"`.

Orders Table Interface (`/dashboard/orders`):
- Single Orders View:
  * Columns: Order Code, Recipient Phone, Network Badge, Bundle Size, Amount (GHS), Status Badge,
    Created Date, Actions ("Report Not Received", "View History").
  * Filters: Carrier dropdown (MTN, Telecel, AT), Status dropdown, Date Range filter (Today, Yesterday,
    Last 7 Days, Last 30 Days, Custom Range), Search query (phone or order code).
  * Direct Export to Excel: Download filtered orders as an Excel file.

10. WALLET, TOP-UP, PAYSTACK & "SEND & CLAIM" MOMO ENGINE
====================================================================================================
Double-Entry Wallet Architecture:
- `user.balance`: Float representing Ghana Cedis.
- Every balance mutation requires a matching `WalletTransaction` row (`TOPUP`, `DEBIT`, `REFUND`, `ADJUSTMENT`).

Method 1: Instant Paystack Top-Up
1. User enters top-up amount (bounded by `paystack_min_topup` and `paystack_max_topup`).
2. Calls `POST /api/billing/paystack/initialize` -> Returns Paystack checkout URL.
3. User completes payment via Mobile Money prompt or Card.
4. Two-Way Verification:
   - Server-to-server webhook `POST /api/billing/paystack/webhook` with HMAC SHA-512 signature.
   - Client-side verification button `POST /api/billing/paystack/verify` for instant resolution.

Method 2: Automated "Send & Claim" MoMo Top-Up (`src/lib/send-claim.ts`)
1. Merchant MoMo SIM Configuration:
   - Admin configures merchant SIM network, phone number (e.g. `0244000000`), and account name.
2. Android SMS Forwarder Webhook (`POST /api/webhooks/momo/sms`):
   - Android phone with merchant SIM runs an SMS forwarder app.
   - Forwards SMS alerts with secret key authentication (`SMS_FORWARDER_SECRET`).
   - Regex parser extracts: Transaction ID, amount, network, sender phone.
   - Inserts `IncomingMomoTransaction` with status `AVAILABLE`.
3. Reseller Claim:
   - Reseller transfers money from their phone to merchant SIM.
   - Reseller enters Transaction ID and claimed amount on `/dashboard/billing`.
   - Rate limiting: Max 5 failed attempts per 15 minutes.
4. Automatic Matching:
   - Server finds matching `IncomingMomoTransaction`.
   - Marks SMS as `CLAIMED`, creates `SendClaim` as `APPROVED`, credits user wallet,
     records `WalletTransaction` of type `TOPUP`, and sends email confirmation.

14. MULTI-API TELECOM PROVIDER ROUTING & AUTOMATION ENGINE
====================================================================================================
Architecture (`src/lib/provider-apis/router.ts`):
- Vendor-agnostic telecom dispatch abstraction.
- Connects to external telecom fulfillment APIs without hardcoding to any single vendor.
- Multi-Provider Settings in `SystemSetting`:
  * `provider_routing_enabled`: Master switch ("true"/"false").
  * `provider_routing_auto_dispatch`: If true, orders dispatch immediately upon placement.
  * `provider_routing_default`: Default provider key (e.g. "PRIMARY_PROVIDER").
  * Per-Network Provider Route Mapping:
    - `provider_route_MTN`: Provider key assigned for MTN orders.
    - `provider_route_TELECEL`: Provider key assigned for Telecel orders.
    - `provider_route_AIRTELTIGO`: Provider key assigned for AT orders.

Dispatch Lifecycle for Single Orders:
1. When an `Order` is created (via Web, Storefront, or Developer API):
   - Router checks if `provider_routing_enabled` and `provider_routing_auto_dispatch` are true.
   - Looks up the assigned provider for `order.network`.
2. Provider Client:
   - Formats payload according to provider REST specification.
   - Submits HTTP POST request to provider endpoint with API key and idempotency reference.
   - Logs request payload, response payload, status code, and latency in `OrderApiLog`.
3. Order State Update:
   - If provider accepts: Updates `order.status = "PROCESSING"`, saves `providerReference`.
   - If provider rejects: Updates `order.status = "FAILED"`, records sanitized failure note.

Provider Webhook Receiver & Polling Sync:
- Webhook Handler (`POST /api/webhooks/providers/telecom`):
  * Upstream providers deliver status updates: `processing`, `delivered` (mapped to `SUCCESS`), `failed`.
  * Verifies HMAC signature, finds matching order by `providerReference`, updates `order.status`.
- Periodic Sync Cron (`GET /api/cron/provider-sync`):
  * Background cron queries orders in `PROCESSING` status older than 5 minutes and queries
    provider status API to ensure no orders remain stranded.
